# 评测方法

## 设计目标

评测同时回答三个问题：

1. 模型没有 Skill 时表现如何？
2. Skill 能被自动识别和触发吗？
3. Skill 被确定加载后，是否真正改善输出？

因此设置三个受控条件：`D0`、`C_auto`、`C_forced`。除 Skill 可用方式外，模型、Prompt、权限、环境、TestCase 与重复次数必须保持一致。

## 难度维度

- L1 直接识别：缺陷局部可见，主要考查基本检查覆盖；
- L2 跨上下文推理：需要连接多个函数、文件或状态；
- L3 系统行为推理：涉及并发、生命周期、安全边界或架构约束。

三个层级对应从局部模式识别到系统性推理的能力递进，避免测试集只奖励某一种代码审查风格。公开 Beta 只有一个 L3 合成演示案例，因此不计算综合难度权重。正式数据集的样本比例和权重必须在运行前冻结，并通过人评校准，不能根据结果事后调整。

## TestCase 来源

公开仓库仅包含原创合成案例，确保可再分发。完整评测可以混合：

- 人工固定用例：覆盖关键业务风险，提供稳定可比较的锚点；
- 自动生成候选：扩大语言、框架和缺陷组合覆盖；
- 人工复核后冻结：生成并不等于可直接评测，必须去重、校验可执行性、消除提示泄漏并确定断言。

因此不能只回答“有多少条自动生成”：应同时记录总量、人工/生成比例、去重后数量、难度分布和冻结版本。

## 分数计算

计分顺序固定：

1. 每个原子断言得到 verdict；
2. Qualification 决定运行能否计分；
3. 只聚合 `scoring_eligible=true` 的运行；
4. 同时报告有效样本数与 Inconclusive 数量，防止仅看通过率；
5. 对重复运行报告均值、方差或置信区间。

当前离线演示的 33% 通过率是预置回放产生的流程示例，不是模型评测结果。

## 模型与 Judge 选择

课程原型采用不同模型做 Candidate 对照，并用能力更强、结构化输出更稳定的模型承担 Judge，目的是降低同源偏差并提高复杂代码语义理解。但“模型更强”不是充分证据：正式上线前仍需盲化样本、固定 Prompt、多人标注金标准，并测量 Judge 与人评的一致率、误判类型和重测稳定性。

公开 Beta 默认使用确定性规则 Judge，确保任何人无需凭证即可复现。LLM-as-a-Judge 属于后续可替换 Adapter，而不是当前离线结果的来源。
