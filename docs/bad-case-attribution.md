# Bad Case 责任归因

## 为什么是四个方向

四类不是在声称“世界上只有四种错误”，而是按照一次评测的数据流划分四个责任域：

1. `PLATFORM_ERROR`：任务未被可靠执行，例如超时、权限或 Runner 故障；
2. `EVALUATION_ASSET`：执行正常，但 TestCase、输入、GT 或 Rubric 有误；
3. `SKILL_EXECUTION`：资产正确，但 Skill 没有加载、触发或按预期执行；
4. `VALID_MODEL_FAILURE`：前三层正常且证据充分，候选结果仍未满足断言。

证据不足单独记为 `INCONCLUSIVE`。新的具体故障应先归入这四个责任域，再在域内扩展 subtype，而不是随意增加互相重叠的顶层类别。

## 难点具体在哪里

同一个“没有发现缺陷”的结果，表面完全相同，真实原因可能是模型不会、Skill 没触发、输入发错或运行中断。仅看最终文本无法区分，必须把运行链路、输入快照、Skill 哈希、Trace 和输出关联起来，并判断哪个节点最先偏离预期。

## 第一个真实偏离点流程

```text
检查 Runner
  否 → 排除结果，修复 Runner，同一输入定向重跑
  是 → 检查评测资产
         否 → 排除结果，修订并重新冻结 TestCase
         是 → 检查 Skill 是否应加载且实际加载
                否 → 排除结果，修复触发/执行机制
                是 → 检查证据是否充分
                       否 → Inconclusive，补采证据
                       是 → Judge 结果失败则记为有效模型失败
```

## 找到偏离点之后做什么

1. 保存原始失败记录，禁止覆盖；
2. 记录 root cause、first deviation、证据引用和处置动作；
3. 修复对应责任域，而不是修改其他层掩盖问题；
4. 使用相同输入创建新的定向重跑；
5. 比较修复前后 Trace 与结果；
6. 通过后加入回归集，并保留关联标识。

这形成“发现 → 归因 → 修复 → 定向重跑 → 回归验证”的闭环。
